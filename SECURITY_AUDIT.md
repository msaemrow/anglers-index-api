# Authorization and error-handling review

Reviewed the currently registered API routes on October 20, 2026. This source review and regression coverage do not replace production network checks or future reviews when routes change.

## Access policy

| Resource | Read policy | Write policy |
| --- | --- | --- |
| Account profiles | Authenticated owner or admin; user list admin-only | Profile updates are self-only; deletion is self or admin |
| Catches | Lists/analysis scoped to authenticated owner; detail owner or admin | Creation uses authenticated owner; edits/deletion owner or admin |
| Catch photos | Owner or admin, through authenticated endpoints | Owner or admin; storage paths/filenames are server-controlled |
| Trips | Authenticated owner, with owned catch counts/details | Authenticated owner; attachment verifies both trip and catch ownership |
| Tackle box | Authenticated owner, including for admins | Authenticated owner; supplied user IDs cannot select another owner |
| Lure catalog | Public shared catalog fields only; optional owner filter requires that same authenticated user | Creation requires login and assigns current owner; edit/delete admin-only |
| Lake/species catalogs | Public catalog; personal-best joins require current user and use their ID | Admin-only |
| Master Angler reviews | Admin-only queue | Admin-only decisions; eligible catch submission is automatic |
| Certificates | Produced from owner/admin-accessible approved catches | Generation requires login and owner/admin permission |
| Weather provider lookup | Login required | No user-owned record is changed |
| Dashboard | Login required; personal data uses current owner; review preview admin-only | No direct client-controlled ownership |
| Login/signup | Login public; signup blocked unless explicitly enabled by server environment | Signup accepts account fields only, never an admin flag |
| Logout | Login required | Revokes only the authenticated signed session ID |

The unused approved-submissions controller also now checks owner/admin access before any query. No new route was added for it.

Public lure queries now select only id, brand, name, color, and size. They do not join owner profiles or return owner IDs/emails. The historical hardcoded owner-3 inclusion was removed from personal filtering; filtering is scoped to the authenticated owner. The current Vue catalog calls do not use that optional filter.

Trip deletion's catch-unlink operation includes the authenticated user in its query. Catch creation, account signup/update, and lure creation continue to whitelist writable fields so clients cannot assign ownership or admin permissions. The species deletion controller's undefined model reference was corrected while reviewing that admin write path.

Shared catalog access remains intentional. Swagger, the root message, and the test route remain public; production documentation/test-route restrictions are tracked separately in SECURITY_BACKLOG.md.

## Error responses and logging

- helpers/errors.js supplies application-authored public errors, safe unexpected/database error responses, request IDs, and a final Express error handler.
- JSON body parsing, oversized body, unsupported encoding, CORS rejection, and unexpected async failures return JSON without exception messages or stack traces, including in development mode.
- Controllers no longer return raw err.message/error.message values. Database validation, duplicate, and relationship conflicts use fixed public messages.
- Private server error logs are JSON records containing time, operation, request ID, HTTP method/route template when available, authenticated numeric user ID when available, error category, and an allowlisted error code. They deliberately omit exception messages/stacks, SQL, headers, request bodies/query values, and Axios configuration/provider URLs, which may contain credentials.
- X-Request-ID is generated by the API rather than trusted from the client and can be used to correlate a failed request with server logs.
- Authentication-store, provider, photo-storage, and database-startup failures also use this safe logging path. Application-authored validation responses remain useful to the user.

This follows the separation of public responses and private diagnostics described in the [OWASP error-handling guidance](https://cheatsheetseries.owasp.org/cheatsheets/Error_Handling_Cheat_Sheet.html) and uses a final middleware handler as described by [Express](https://expressjs.com/en/guide/error-handling/).

## Verification

```sh
node --test tests/*.test.js
```

107 tests passed; the opt-in PostgreSQL session test is skipped in the default run. New tests cover the protected-route/admin matrix, cross-user catch writes, safe catalog query projections, controller database/provider failures, parsing/CORS/uncaught failures, and exclusion of sensitive values from both responses and logs. Existing tests also cover account/tackle-box ownership, trip/catch attachment, photos, certificates, signup field whitelisting, and session revocation.

No database migration or frontend change is required for this review. Restart the API to load the changes.
